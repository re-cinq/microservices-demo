# Quickstart: Star ratings on the product list

**Feature**: [spec.md](spec.md) · **Plan**: [plan.md](plan.md)

Short, mechanical steps to (1) verify the design assumptions in your local repo before coding starts, and (2) run the loop you'll use while implementing. Implementation itself is generated by `/speckit.tasks` and `/speckit.implement`.

## 0. Preconditions

- You are on branch `attendee/daniel-tufvander` in `/Users/danieltufvander/Lovable app Wheel/microservices-demo`.
- `protoc` and the Go gRPC plugins are installed locally (used by `genproto.sh`). If not, run `genproto.sh` once first and follow its `command not found` hints.
- `skaffold` is installed and your `kubectl` context points at your cohort cluster (or `minikube`).

## 1. Verify the canonical proto location

```bash
grep -n "message Product" protos/demo.proto
```

You should see a single match. Confirm `Product` currently has fields 1–6 and that the next free number is `7` (research D9). If anything has been added since this plan was written, pick the next unused number and update `contracts/service-contract.md` accordingly.

## 2. Verify the data path

```bash
head -20 src/productcatalogservice/products.json
```

Confirm the file is JSON of the shape `{"products": [ {id, name, description, picture, priceUsd, categories}, … ]}`. Adding a new sibling key `"rating": <float>` to each product is the seeding step.

## 3. Implementation loop (run during `/speckit.implement`)

The following commands are what each task will iterate on; capture for muscle memory:

```bash
# 3a. edit protos/demo.proto, add `float rating = 7;` to message Product

# 3b. regenerate Go stubs in both services
( cd src/productcatalogservice && ./genproto.sh )
( cd src/frontend            && ./genproto.sh )

# 3c. edit src/productcatalogservice/products.json — add a rating field to every product

# 3d. extend src/productcatalogservice/product_catalog_test.go with a load-and-assert test

go test ./src/productcatalogservice/...

# 3e. edit src/frontend/handlers.go — extend the productView struct with `Rating float32`;
#     populate from p.GetRating() in the homeHandler loop.

# 3f. edit src/frontend/templates/home.html per contracts/ui-contract.md

# 3g. add CSS rule for `.hot-product-card-rating` in src/frontend/static/styles/<existing-file>.css

# 3h. local run via skaffold
skaffold dev --port-forward
```

## 4. Manual acceptance verification

Mapped to acceptance scenarios in [spec.md](spec.md):

| Scenario | How to verify |
|---|---|
| AS-1: every product card shows a rating | Open the home page; visually scan every card. |
| AS-2: rating matches the catalogue value | Pick one product whose `rating` you seeded in `products.json`; compare to the rendered stars using the table in [data-model.md](data-model.md). |
| AS-3: ratings stable across page loads | Reload the home page three times; confirm the same products show the same ratings each time. |

Additional manual checks tied to the UI contract:

- Inspect a card with `5.0`: five filled stars.
- Inspect a card with a half-star value: matches the table in `data-model.md`.
- Temporarily set one product's `rating` to `0.0` in `products.json` (and revert) — that card should render no widget; the rest of the card is unchanged.
- Use VoiceOver / NVDA on one card; confirm it reads "Rated X.X out of 5 stars" exactly once.

## 5. What to leave alone

The following MUST NOT be touched (constraint C-004 in spec, and research D10):

- `kubernetes-manifests/`, `helm-chart/`, `istio-manifests/`, `kustomize/`
- `skaffold.yaml`, `cloudbuild.yaml`
- `.github/`, anything under `release/`
- Any other service under `src/` than `productcatalogservice` and `frontend`

If a change there appears necessary, stop and re-read the spec's Constraints section.
